# 9 ファイルシステムの基礎とGo言語の標準パッケージ

## 9.1 ファイルシステムの基礎

inodeは、ファイルのメタデータを保持している。
その物理的な格納場所は、ストレージにある。

ストレージ内にファイルの情報を固定長のバイトの配列として格納しているが、それの中の一部が管理領域として扱われて、
その中にinodeの情報が格納されている。(各ファイルでinode情報を含む管理領域は1つだけ。長大なファイルであっても、inode情報は1つだけ。)

### 9.1.1 複雑なファイルシステムとVFS

/procは仮想的なファイルシステムで、カーネルの情報を提供する。
ここはカーネル内部のスナップショットがファイルとして表現されている。

VFSは、Virtual File Systemの略で、Linuxカーネルが提供する抽象化されたファイルシステムのインターフェース。
VFSがあればファイルシステムが異なるものであっても、同じインターフェースでアクセスできる。
ext4やXFSなどのファイルシステムは、VFSを通じてアクセスされる。

最近はジャーナリングファイルシステムというものになっているらしい。
これは、ファイルの更新においてメタデータと実データの変更を同一のトランザクション内で行うように工夫したものである。
ジャーナリングファイルシステムでないときは、不整合が起きた時にはfsckコマンドを使って修復する必要があったが、
- めちゃくちゃ時間がかかる
- 不整合が起きると、データが失われる可能性がある

という課題を抱えていた。
これらの課題を解決するために、ジャーナリングファイルシステムが開発された。
ジャーナリングファイルシステムでは、メタデータの変更を先に行い、その後に実データの変更を行う。
これによって、仮に不整合が起きたとしても、メタデータの変更が先に行われているため、データの整合性を保つことができる。
不整合が起きた場合には、ジャーナルに記録された情報をもとに、ファイルシステムを復旧する。

### 9.1.2 論理ボリュームマネージャLVM

## 14.7 syncパッケージ

Goにおいて、goroutine間の同期はチャネルとselectで事足りるが、多言語からの移植を考慮して、syncパッケージが用意されている。

pthreadなる仕組みがあるが、Goにおいてそれと同様のことをするためのライブラリがsyncパッケージである。

https://ja.wikipedia.org/wiki/POSIX%E3%82%B9%E3%83%AC%E3%83%83%E3%83%89

### 14.7.1 sync.Mutex/sync.RWMutex

sync.Mutexはそのコードを通るgoroutineを1つに制限する事ができる。

チャネルとの使い分けについては、sync.Mutexは状態管理やキャッシュ管理に使う。

sync.RWMutexは、読み取り専用のgoroutineを複数許可することができる。

状態管理についてはsync.Mutexを使い、キャッシュ管理についてはsync.RWMutexを使うのが良い。

TryLock()を使うことで、ロックがかかっていないことを確認してからロックを取得することができる。

### 14.7.2 sync.WaitGroup

sync.WaitGroupは、goroutineの終了を待つためのもの。

### 14.7.3 sync.Once

sync.Onceは、1度だけ実行される処理を定義するためのもの。
基本的に初期化処理のために使われる。
普通はinitで初期化処理をするが、初期化処理が必要な時まで遅延させたい時にsync.Onceを使う。

### 14.7.4 sync.Cond

sync.CondはWaitしたタイミングで処理が止まり、Broadcast()やSignal()が呼ばれたタイミングで処理が再開される。

Signalについてはチャネルの利用で事足りるので、あまり使われない。
Broadcastはtlsやhttp2の実装において、ハンドシェークが終わったらワーカースレッドを起動するために使われている。

### 14.7.5 sync.Map

sync.Mapは、並行処理において安全にマップを扱うためのもの。

## 14.8 sync/atomicパッケージ

[不可分操作](https://ja.wikipedia.org/wiki/%E4%B8%8D%E5%8F%AF%E5%88%86%E6%93%8D%E4%BD%9C#:~:text=%E4%B8%8D%E5%8F%AF%E5%88%86%E6%93%8D%E4%BD%9C%EF%BC%88%E3%81%B5%E3%81%8B%E3%81%B6%E3%82%93%E3%81%9D%E3%81%86,%E3%81%AB%E8%A6%8B%E3%81%88%E3%82%8B%E3%82%82%E3%81%AE%E3%82%92%E3%81%84%E3%81%86%E3%80%82)を実現するためのパッケージ。

不可分操作とは、アトミック操作とも呼ばれていて、
- 該当操作による途中の状況は他のプロセスから見る事ができない
- 該当操作が失敗した場合は、操作をする前の状態に戻る

という条件を満たす。

### 14.8.1 メモリマップドI/Oとsync/atomic

biscuit OSなるGolangで書かれたOSがあるらしい。

それにおいて、メモリマップドI/Oの部分でsync/atomicパッケージを使っている。

メモリマップドI/Oとは、OSが外部デバイスとやりとりするための仕組みの1つである。

sync/atomic を使うのはメモリ操作がアウトオブオーダで並べ替えられないようにするため。

## 16.3 スライスなど

スライスの実態は、
- 配列の先頭要素へのポインタ
- スライスの長さ(len)
- スライスの容量(cap)

lenはそのスライスの実際の長さで、capは事前に保有しておく配列の長さを指す。

### 16.3.1 スライスの作成方法
既存の配列を参照するスライスを作る。
```go
a := [5]int{1, 2, 3, 4, 5}
s := a[1:3] // [2, 3]
```

または、make関数を使ってスライスを作る。
```go
s := make([]int, 5) // 長さ5、容量5のスライスを作成
```

### 16.3.2 スライスのメモリ確保とパフォーマンス改善のヒント

スライスにappendする際に、capが足りない場合は、新たに領域を確保した上で古い配列をコピーする。
capは、長さが512までは2倍に増やす。それ以降はペースが落ちる。

https://github.com/golang/go/blob/master/src/runtime/slice.go#L296

元々のスライスの予定長さが決まっているような場合は、初めにその数分だけcapを用意しておいた方がパフォーマンスが良い。

### 16.3.3 マップとパフォーマンス改善のヒント
マップは各要素をバケットという箱に収めている。
1つのバケットは8つの要素を収めることができる。
マップのキーのハッシュ値の下nビットを使って、バケットが導出できる。
該当のバケットから要素を特定する際には、上位の8ビットを用いる。

マップもmakeを使って最初にcapを決めて作成する。
スライスと同様に、入れる個数が予測できるなら最初からその個数分確保しておくとパフォーマンスが良い。
